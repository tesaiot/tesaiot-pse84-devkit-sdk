The sensors module is compiled from modsensors.c and its five modsensors_*.c companions, none of which is in the mtb-only package. The C entry points underneath every call in this chapter are in both packages, and are listed in The C entry points (both packages); the mtb-only path to them is J1 — The sensor bus and its lock.

Learning goal

After this chapter you can read every sensor on the board from the REPL, predict what each call returns and in what unit, and — more usefully — say what each one does when the hardware is not there. You will also know which single call gives you a coherent six-axis reading, and why the other five ways of getting the same six numbers are not equivalent.

Note
Thin evidence, stated up front. This package contains no Python files at all: find template -name "*.py" returns build tooling only. The one in-package usage exemplar for the whole peripheral surface is README.md:130-132, which shows sensors.scan() and sensors.read_all(). Every other example in this chapter is authored and labelled as such. Nothing here asks you to run a file you do not have.

The real firmware sequence

The six are not symmetric. sensors names six sensors — bmi270, dps368, sht40, bmm350, capsense, pot (modsensors.c:1218-1223) — but only the BMI270 is unconditional. The other five each sit behind a BSP_HAS_* flag in the registration table (modsensors.c:1341-1362), and on a build where the flag is 0 the sub-module is not merely inert: the attribute does not exist. sensors.sht40 raises AttributeError, not an OSError. Ask hasattr(sensors, 'sht40') when you mean "is this board fitted with one".

init() is loud about partial failure and honest about total failure. sensors.init() (modsensors.c:523) raises OSError only if the bus itself will not come up. Each sub-driver that fails prints one line and clears a flag, so the call returns False while the healthy sensors keep working:

if (!bmi270_init()) {
mp_printf(&mp_plat_print, "sensors: BMI270 init failed\n");
ok = false;
}

The same shape repeats for DPS368, SHT40, BMM350, CapSense and the pot, each inside its own #if BSP_HAS_* (modsensors.c:538-571).

read_all() takes one lock for the whole sweep. It opens with sensor_i2c_lock(200) — twice the per-call timeout, because it is doing six sensors' work — and builds the dict inside it (modsensors.c:820). A sensor that fails its read contributes no key; it does not contribute a key holding None. Code that does d['sht40']['temperature'] without checking membership will raise KeyError on a board whose SHT40 stopped answering, and that is the intended signal.

The six, call by call

Units, returns and failure modes. The full table with line numbers is MicroPython — the sensor sub-modules.

Sensor Calls Unit On failure
BMI270 acceleration(), gyroscope(), temperature(), motion(), chip_id() m/s², deg/s, °C OSError with the sensor named

SHT40 temperature(), humidity(), temperature_humidity() °C, RH OSError
BMM350 magnetic(), heading(), chip_id(), cal_reset(), cal_status() µT, degrees 0..360 with 0 = north OSError
CapSense read(), buttons(), slider() bool, bool, 0..100 OSError naming the answering core
Pot read(), percent(), voltage() 0..65535, 0..100, 0..3.3 V OSError

Three notes the table cannot carry:

  • bmi270.temperature() is die temperature, not room temperature. It reads the IMU's internal sensor and sits several degrees above ambient. For room temperature use sht40.temperature() or dps368.temperature().
  • bmm350.heading() needs cal_status() before you trust it. The heading is derived from the raw X/Y vector against the running calibration offsets (sensor_bmm350.c:791 and :829); cal_reset() (modsensors_bmm350.c:54) restarts that estimate, and cal_status() (:62) is how you find out whether it has converged.
  • pot.voltage() scales against a constant, not a measurement. POTENTIOMETER_VDDA_V is 3.3f (sensor_potentiometer.c:19), and the source records that the schematic says VDD_1V8. The two have not been reconciled, and the standing instruction is not to assert either until P15[1] is metered. Treat voltage() as a scaled count with a documented open question, and prefer read() or percent() for anything that matters.

The one call that is not a convenience wrapper

sensors.bmi270.motion() (modsensors.c:230) returns all six axes under one bus lock:

sensor_i2c_lock(100);
bool ok = bmi270_read_accel(&ax, &ay, &az) &&
bmi270_read_gyro(&gx, &gy, &gz);
sensor_i2c_unlock();

Calling acceleration() and then gyroscope() gives you the same six numbers and is not the same thing: those are two lock/unlock pairs, and the bus belongs to somebody else in between. On a still board you will never see the difference. On a board being shaken — which is every board a motion model is trained on — the two vectors describe different instants, and the fused result is wrong in a way no unit test catches. Use motion() whenever the six numbers are consumed together.

Step by step

Step 1 — Bring the sensors up and read the console

>>> import sensors
>>> sensors.init()
What you should observe
On a fully healthy board, one line — sensors: all sensors initialized OK (modsensors.c:573-575) — and then True. Every other line this call can print is a failure line, one per sub-driver, in the form sensors: BMI270 init failed (modsensors.c:533-536, and the same shape for each flag-gated sensor through :571). A False return with one such line means five sensors are fine and one is not; an OSError means the bus itself did not come up and nothing was read at all.

Step 2 — The two calls with a shipped exemplar

>>> sensors.scan()
>>> sensors.read_all()
What you should observe
scan() returns the answering addresses (J1 — The sensor bus and its lock). read_all() returns a dict whose keys are exactly the sensors that answered this sweep — bmi270, and then dps368, sht40, bmm350, capsense, pot as the board and the flags allow. A sensor that failed its read is absent. This is the pair shown in README.md:130-132, and the only peripheral example that ships inside the package.

Step 3 — A coherent six-axis read

Example (authored — no shipped call site)
import sensors
sensors.init()
ax, ay, az, gx, gy, gz = sensors.bmi270.motion()
print("accel m/s^2:", ax, ay, az)
print("gyro deg/s :", gx, gy, gz)
What you should observe
Six floats. At rest, one accelerometer axis reads about 9.8 and the other two about 0 — which axis depends on how the board is lying — and all three gyro values sit near 0 with a little noise. Tilt the board and the 9.8 migrates between axes. This call has no call site anywhere in the shipped tree, which is why the example above is authored rather than lifted.

Step 4 — Is the IMU actually alive?

Example (authored — no shipped call site)
import sensors
sensors.init()
print(hex(sensors.bmi270.chip_id()))
What you should observe
0x24 on a healthy BMI270 (modsensors.c:253, driver at sensor_bmi270.c:65). Any other value, or an OSError, separates "the sensor is not talking" from "the sensor is talking and reporting nonsense" — a distinction the reading calls cannot make for you, because a wedged bus and a sensor stuck at zero both produce zeros. Zero-caller call: authored example.

Step 5 — When the magnetometer is the one that is wrong

Example (authored — no shipped call site)
import sensors
sensors.init()
d = sensors.bmm350_diag()
print(d['step'], d['init'], d['id'])
print(d['wr_st'], d['wr_ev'], d['rd_st'], d['rd_ev'])
What you should observe
A 12-key dict: step, init, att, s_init, s_en, pres, forced, wr_st, wr_ev, rd_st, rd_ev, id (modsensors.c:1269-1315; the driver side is bmm350_diagnose(), sensor_bmm350.c:863). It is deliberately kept to twelve fields so the REPL does not truncate it. The companion sensors.bmm350_debug() (modsensors.c:1315) prints a register dump instead of returning anything. Both are zero-caller diagnostics; the examples here are authored.

The reason this sensor gets its own diagnostics and the others do not: the BMM350 is on I3C, not on SCB0, so it can fail entirely on its own while the bus and every other sensor are healthy (J1 — The sensor bus and its lock).

Traps

Warning
A missing key is the API, not a bug. read_all() omits a sensor that failed; it never stores None. Guard with in before indexing.
A missing sub-module raises AttributeError. On a build with BSP_HAS_SHT40=0 the name sensors.sht40 does not exist. Feature-test with hasattr, not with try: ... except OSError.
Do not rebuild motion() out of two calls. Two lock/unlock pairs are not one; see The one call that is not a convenience wrapper.
bmi270.temperature() is not the room. Reporting it as ambient is a documentation error that has been made before.
pot.voltage() carries an unresolved reference-voltage question. The code scales 3.3 V; the schematic says VDD_1V8. Do not "fix" either side without metering P15[1] (sensor_potentiometer.c:6-19).
sensors.snapshot() does not exist in this package — it is registered only under #ifdef USE_KIT_PSE84_EVAL_EPC2 (modsensors.c:1330-1332) and no Eva BSP ships here. Neither does sensors.light(), which appears in an older example corpus and in no module table in this tree.
