เป้าหมายของหัวข้อนี้

แยกให้ออกระหว่าง คำสั่ง กับ คำขอ stop() เป็นคำสั่ง unload() เป็นคำขอที่เครื่องยนต์ปฏิเสธได้ ส่วน stage_load() ไม่มีการตอบรับใด ๆ เลย ต้องยืนยันด้วยการเฝ้าดูจำนวนใน registry ว่าเพิ่มขึ้น ทั้ง 3 อย่างมีเส้นทางการตรวจสอบต่างกัน และบทนี้เดินครบทั้ง 3 เส้นทาง

ลำดับการทำงานจริงของเฟิร์มแวร์

Stop edge_ai.stop() (modedgeai.c:543-552) ส่ง EDGE_AI_CMD_STOP แล้วจึงยืนยันสถานะว่าง (idle) แบบพยายามให้ดีที่สุด ฝั่ง CM55 ล้าง s_running เรียก ai_engine_stop() — ซึ่งเพียงตั้ง s_active = -1 (ai_engine.c:1864) — แล้วจึง ไล่อัตราเซนเซอร์ลง:

ที่มา
ยกมาจาก deepcraft_task.c:679-690 (คอมไพล์รวมอยู่ใน archive สำเร็จรูป ไม่ได้ส่งมอบมาเป็นซอร์ส)

deepcraft_task.c:682-686 บันทึกไว้ว่าเหตุใดการเรียกปรับอัตราจึงเป็นข้อบังคับ: หากไม่เรียก accelerometer จะค้างอยู่ที่ 50 Hz และแย่งทรัพยากรจนเซนเซอร์ของแดชบอร์ดขาดแคลน อัตรานี้ยังถูกยืนยันซ้ำทุก 2 s เพื่อเป็นมาตรการแก้ไขตัวเอง:

ที่มา
ยกมาจาก deepcraft_task.c:811-823 (คอมไพล์รวมอยู่ใน archive สำเร็จรูป ไม่ได้ส่งมอบมาเป็นซอร์ส)

Unload edge_ai.unload(i) (modedgeai.c:406-419; ข้อกำหนดการเรียกใช้ที่ :400-405: "A request, not a command… Send `stop()` first, then read `edge_ai.diag()` to see whether it completed or was refused") ฝั่ง CM55 นำเข้าคิว:

ที่มา
ยกมาจาก deepcraft_task.c:691-695 (คอมไพล์รวมอยู่ใน archive สำเร็จรูป ไม่ได้ส่งมอบมาเป็นซอร์ส)

task ของการอนุมานให้บริการคำขอนี้ที่ต้นรอบการทำงาน (ai_engine.c:1401-1416) และต้องการ s_current < 0 && s_active < 0 — กล่าวคือการหยุดต้องถูก สังเกตเห็นแล้ว ไม่ใช่เพียงถูกร้องขอ — บวกกับโมเดลที่พร้อมและมี finalize จากนั้นจึงเพิ่มค่า s_unload_done มิฉะนั้นจะเพิ่ม s_unload_refused เหตุผลที่ต้องมี unload อยู่เลย (ai_engine.c:1255-1260): finalize() ของ DEEPCRAFT คืนหน่วยความจำของโมเดลแต่ทิ้ง handle ให้ห้อยอยู่ และ enqueue() ก็ยังคืนค่าว่าสำเร็จต่อไป การล้าง s_model_ready จึงบังคับให้การ select ครั้งถัดไปเดินเส้นทาง cold-init "แทนที่จะป้อนข้อมูลให้ซากศพ"

โมเดล staged edge_ai.stage_load(...) ส่ง MODEL_LINK_CMD_LOAD_STAGED และฝั่ง CM55 จัดการมันใน task context ไม่ใช่ใน callback ของ pipe เด็ดขาด:

ที่มา
ยกมาจาก deepcraft_task.c:696-715 (คอมไพล์รวมอยู่ใน archive สำเร็จรูป ไม่ได้ส่งมอบมาเป็นซอร์ส)

deepcraft_task.c:700-711 ให้เหตุผลไว้ว่า mtb_ml_model_init() จองหน่วยความจำจาก heap ของ LVGL และการลงทะเบียนต้องใช้ critical section ส่วนการตรวจสอบก่อนไว้วางใจอยู่ที่ ai_model_staged.c:452-470 ไม่มีเหตุการณ์ตอบรับใด ๆ ฝั่ง MicroPython จึงวนอ่านจำนวนใน registry แทน (modedgeai.c:808-828)

ทีละขั้น

ขั้นที่ 1 — หยุดโมเดลที่กำลังทำงาน

>>> edge_ai.select(0); edge_ai.stop()
>>> edge_ai.active()
-1

สิ่งที่ควรสังเกต active() คืนค่า −1 เมื่อ task ของการอนุมานสังเกตเห็นการหยุดแล้ว บนหน้าจอ badge เปลี่ยนเป็น CHIP_STOPPED (page_edge_ai.c:1338 — เป็น CHIP_STOPPED ไม่ใช่ CHIP_FAIL เพราะ stack_words() ไม่เป็นศูนย์) ส่วนแถวเซนเซอร์ของแดชบอร์ดกลับสู่จังหวะปกติภายในราว 2 s

ขั้นที่ 2 — สั่ง unload ขณะที่ยังทำงานอยู่ แล้วดูการปฏิเสธ

>>> edge_ai.select(0)
True
>>> before = edge_ai.diag()['unload_refused']
>>> edge_ai.unload(0)
>>> edge_ai.diag()['unload_refused'] - before
1

สิ่งที่ควรสังเกต unload_refused เพิ่มขึ้นหนึ่ง และ unload_done ไม่ขยับ เพราะเครื่องยนต์ไม่ได้อยู่ในสถานะว่าง คำขอจึงถูกปฏิเสธและถูกนับไว้ ตัวนับนั้น คือคำตอบ

ขั้นที่ 3 — สั่ง unload หลังหยุดแล้ว แล้วดูการทำงานสำเร็จ

>>> edge_ai.stop()
>>> before = edge_ai.diag()['unload_done']
>>> edge_ai.unload(0)
>>> edge_ai.diag()['unload_done'] - before
1

สิ่งที่ควรสังเกต unload_done เพิ่มขึ้น การ select(0) ครั้งถัดไปจะเดินเส้นทางโหลดแบบเย็นเต็มรูปอีกครั้ง (นานถึง 15 s) ซึ่งเป็นผลที่ตั้งใจไว้ ให้วนอ่านคู่ unload_done/unload_refused ไปด้วยกัน (deepcraft_task.c:377-378 → modedgeai.c:452-455) การอ่านเพียงตัวเดียวไม่บอกอะไรเลย

ขั้นที่ 4 — stage โมเดลหนึ่งตัว แล้วยืนยันด้วยการสังเกต

>>> n0 = len(edge_ai.models())
>>> edge_ai.stage_load(...) # per the edge_ai module reference
>>> len(edge_ai.models()) - n0
1

สิ่งที่ควรสังเกต จำนวนใน registry เพิ่มขึ้นหนึ่ง นั่นคือการยืนยันเพียงอย่างเดียวที่มี หากไม่เพิ่ม ให้อ่าน edge_ai.diag() เพื่อดูตัวนับฝั่ง staged — staged_rejects และ staged_last_rc ถูกส่งออกมาเป็นคู่ (deepcraft_task.c:380-382) ส่วน staged_heap_free เป็นการอ่านที่ปลอดภัยใน ISR (:379)

ขั้นที่ 5 — ทำให้โมเดล staged เข้าร่วม set

>>> edge_ai.set_define(253, [0, n0]) # n0 = the new row's index

สิ่งที่ควรสังเกต การอ่านกลับด้วย Q_SET แสดงสมาชิกครบทั้ง 2 ตัว หากไม่มี set_define โมเดลที่อัปโหลดเข้ามาจะเข้าร่วม set ที่คอมไพล์มาได้ด้วยการสวมรอยเป็นสมาชิกตัวนั้นทาง ชื่อ เท่านั้น (ai_engine.c:1092-1127) และ set_wants() ไม่ได้หยุดที่คู่แรกที่ตรงกัน ดังนั้นทั้ง 2 ตัวจะถูกป้อนข้อมูลและทั้ง 2 ตัวจะเผยแพร่ผล (modedgeai.c:855-859)

กับดัก

Warning
ห้ามเรียก ai_engine_resume_sensor() ทันทีหลัง ai_engine_set_sensor_rate() ทั้งสองใช้บัฟเฟอร์ CY_SECTION_SHAREDMEM ตัวเดียวกันคือ s_rate_msg และ Cy_IPC_Pipe_SendMessage ทำงานแบบไม่ประสานเวลา memset ที่นำหน้าของ op=1 จึงล้าง op=2 ที่ยังค้างอยู่ให้เป็นศูนย์ และ CM33 อ่านได้เป็น PAUSE (ai_engine.c:522-536) resume_sensor ไม่มีผู้เรียกที่ใดเลย ในเฟิร์มแวร์ที่ส่งมอบ ตัวอย่างที่เขียนขึ้นเองจึงเป็นการส่งแบบยืนเดี่ยว โดยมี anti-pattern กำกับไว้ในกรอบ:
__attribute__((used))
static void bento_ex_ai_engine_resume_sensor(void)
{
/* WRONG — the shared-buffer hazard (see the box above):
*
* ai_engine_set_sensor_rate(100u); // op=2, in flight...
* ai_engine_resume_sensor(); // memset kills it -> PAUSE
*
* RIGHT — set_sensor_rate alone already resumes the push task:
*
* ai_engine_set_sensor_rate(100u); // walk down to dashboard rate
*
* RIGHT — resume as a standalone message, nothing else in flight
* on s_rate_msg (page-leave path, no rate change wanted): */
ai_engine_resume_sensor();
}
Warning
set_sensor_rate ต้องเป็นผู้ส่ง IPC รายเดียวบนบัฟเฟอร์นั้น จุดเรียกที่ส่งมอบมาทั้ง 5 จุดผ่าน dc_desired_sensor_rate() ทั้งหมด
การหยุดต้องถูกสังเกตเห็น ไม่ใช่เพียงถูกร้องขอ unload() ที่ออกตามหลัง stop() ในจังหวะเดียวกันมักถูกปฏิเสธ เพราะ task ของการอนุมานยังไม่ได้ทำงานสักรอบที่ s_current < 0 ให้ตรวจ active() == -1 ก่อน
