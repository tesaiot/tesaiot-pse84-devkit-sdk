variant ที่ใช้ได้
mtb-mpy และ mtb-only

ตารางฝั่ง C บนหน้านี้ใช้ได้กับแพ็กเกจทั้ง 2 ตัว ส่วนตารางของ MicroPython มีการกำกับไว้และแสดงเฉพาะในชุดของ mtb-mpy เพราะแพ็กเกจ mtb-only ไม่มีไฟล์ binding mod*.c มาให้เลยแม้แต่ไฟล์เดียว — ดู ตารางเทียบ variant

หน้านี้คืออะไร

หน้าสำหรับเปิดหาส่วนที่เรียกใช้ได้ของอุปกรณ์ต่อพ่วง: ทุกการเรียก ค่าที่คืนมา และ flag BSP_HAS_* ที่ตัดสินว่าสิ่งนั้นมีอยู่หรือไม่ Tutorial ต่าง ๆ อธิบาย เหตุผล ส่วนหน้านี้มีไว้เพื่อไม่ต้องกลับไปอ่านบทเหล่านั้นซ้ำอีกรอบ

มีข้อเท็จจริงเรื่องขอบเขต 2 ข้อที่กำกับทุกอย่างด้านล่างนี้ และควรระบุไว้ก่อนตารางแรก

  • แพ็กเกจนี้ส่งมอบ BSP มาเพียงชุดเดียว — bsps/TARGET_KIT_PSE84_AI/ สาขา #ifdef USE_KIT_PSE84_EVAL_EPC2 ทุกจุดในซอร์สของเซนเซอร์และ GPIO คอมไพล์ทิ้งไปแล้วที่นี่ และไปถึงไม่ได้จากแพ็กเกจนี้
  • binding ของอุปกรณ์ต่อพ่วงเป็นซอร์สในเทมเพลต ไม่ใช่ archive (ไฟล์ไลบรารีแบบสแตติก .a) ที่คอมไพล์มาแล้ว ไม่มีสิ่งใดใน sdk/docs/ ที่อธิบาย binding เหล่านี้ เพราะไม่ได้อยู่ในไฟล์ .a ที่ส่งมอบตัวใดเลย นั่นคือเหตุที่หัวข้อนี้เป็น Tutorial บวกกับตารางนี้ ไม่ใช่รายการ API ที่ดึงมาจาก nm

Note
ช่องโหว่ของการจัดแพ็กเกจ ซึ่งรายงานไว้ตรง ๆ ไม่ได้กลบเกลื่อน แพ็กเกจ mtb-only ส่งมอบ sensor_capsense.c (I2C โดยตรง) มาให้ แต่ไม่ได้ส่ง sensor_capsense_ipc.c หรือ capsense.mk มาด้วย บนบอร์ด QWA309 ชิป 4000T อยู่บนบัสจอแสดงผลซึ่ง CM55 เป็นเจ้าของ backend แบบตรงจึงไปอ่านผิดบัส นักพัฒนาฝั่ง mtb-only ที่เรียก capsense_read() ในวันนี้จะได้ backend ตัวนั้น รายละเอียดและวิธีเลี่ยงอยู่ใน ทางแยกของ CapSense: หนึ่ง API สอง backend

สองการเรียกที่อาจเคยเห็นจากที่อื่น — ไม่มีทั้งคู่ที่นี่

  • sensors.snapshot() ลงทะเบียนไว้ภายใน #ifdef USE_KIT_PSE84_EVAL_EPC2 เท่านั้น (modsensors.c:1330-1332) แพ็กเกจนี้ไม่ได้ส่ง BSP ของ Eva มาด้วย การเรียกนี้จึงไม่มีอยู่บนบอร์ดใดก็ตามที่สร้างจากแพ็กเกจนี้ ห้ามเขียนโค้ดโดยอ้างอิงการเรียกนี้
  • sensors.light() ปรากฏในคลังตัวอย่างรุ่นเก่าที่อยู่นอกแพ็กเกจนี้ และไม่มีอยู่ในตารางโมดูลใดเลยในต้นไม้ไฟล์นี้ นั่นคือเอกสารที่คลาดจากของจริง (documentation drift) และหัวข้อนี้จะไม่นำต่อไป
