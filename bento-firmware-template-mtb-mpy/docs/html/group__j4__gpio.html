Variant

The gpio module is modgpio.c, which is not in the mtb-only package. There is no C-side equivalent to document for that variant: on mtb-only you drive these pins with the PDL directly (Cy_GPIO_Set / Cy_GPIO_Clr / Cy_GPIO_Read on CYBSP_USER_LED* and CYBSP_USER_BTN1), and the pin table in Pins, buses and addresses is the part of this chapter that still applies.

Learning goal

After this chapter you can drive the five LEDs and read the button, and — more importantly — you can predict what brightness(40) will actually do on each LED, because it is two different mechanisms depending on which pin you picked. This is the best teaching material in the whole peripheral surface, because the wrong mental model produces a demo that appears to work and is measuring nothing.

The real firmware sequence

Five LEDs, one button. led_table[] (modgpio.c:38-50) is built from the BSP aliases and is #ifdef-gated per LED, so NUM_LEDS (:51) is however many the board defines. On this board that is five, in this order:

Index name() BSP alias TCPWM route
0 LED1 CYBSP_USER_LED1 none
1 LED2 CYBSP_USER_LED2 none
2 RGB_RED CYBSP_USER_LED3 P20.6, line 265
3 RGB_BLUE CYBSP_USER_LED4 P20.5, line 264
4 RGB_GREEN CYBSP_USER_LED5 P20.4, line 263

btn_table[] has exactly one entry, NUM_BTNS 1 (modgpio.c:53-59).

The button's name is a correction, and the comment says so. The entry reports "SW2", and the comment above it records why:

Physical silkscreen says SW2 on both the AI Kit and the Eva Kit; the BSP alias chain is CYBSP_USER_BTN1 = CYBSP_SW1, which is the DEFINE's name, not the button's. Reported as "SW1" until 2026-08-20.

If you have older material that calls this button SW1, that material is naming a macro rather than a part. The board says SW2.

Three PWM routes, and only three. s_led_pwm_routes[] (modgpio.c:159-166) maps LED indices 2, 3 and 4 to TCPWM0 group-1 counters 265, 264 and 263, using divider CY_SYSCLK_DIV_16_BIT #3 and period 1000 (:147-149) — 100 MHz / 100 = 1 MHz, period 1000, so a 1 kHz PWM. LED1 and LED2 have no entry. The comment at :143-146 records that divider #4 was tried first and does not exist, and that the failure was silent because return codes were ignored — they no longer are.

Every state change tells CM55. on(), off(), toggle(), value(v), brightness() and hold() all end with gpio_ipc_send_led_state(), so the on-screen GPIO page reflects what the REPL did. The buffer they send through, gpio_ipc_msg, is not static and is shared with modoptiga.c — see Traps.

The honest brightness story

This is the part worth reading twice. led.brightness(pct) (modgpio.c:375) takes one of three paths:

  1. 0 < pct < 100 on a routed pin. led_pwm_set() (:211) programs the TCPWM counter and returns true. The dimming is done in hardware: non-blocking, flicker-free, and it holds the level until the next call. This is what you get on RGB_RED, RGB_BLUE, RGB_GREEN.
  2. pct == 0 or pct == 100. The route is released and the pin is simply driven low or high (:391-403). Cheap, and the common cases cost nothing.
  3. 0 < pct < 100 on a pin with no route — LED1 and LED2. Fall back to a bit-bang: BRIGHT_PERIOD_US 200 µs (5 kHz) on for pct% of the period, repeated BRIGHT_CYCLES 60 times (:372-373). That blocks the VM for about 12 ms, and then it ends dark (:427).

Path 3 ending dark is deliberate, and the comment at modgpio.c:414-426 is a record of a bug being fixed honestly rather than papered over. The code used to finish with Cy_GPIO_Set and claim that kept the dimmed level visible. It did the opposite — the pin sat high, so between calls the LED was at 100% and every level looked identical. The example written to teach duty cycle (set 20, set 60, compare with your eyes) showed one brightness for both, which is how it was found. Ending dark makes the truth visible: on an unrouted pin, a single brightness() call is a 12 ms pulse, and holding a level means calling it in a loop.

hold() is that loop, done properly. led.hold(pct, ms=500) (modgpio.c:444) repeats the same pulse until ms has elapsed, and yields through MICROPY_EVENT_POLL_HOOK between pulses (:474) so Ctrl-C and the IDE Stop button stay alive — brightness() alone is deaf for its 12 ms. It too ends dark.

Note
hold() is always the bit-bang path. It does not consult led_pwm_set(), so calling it on an RGB pin gives you a software-timed hold on a pin that could have done it in hardware. For a steady level on RGB_*, one brightness() call is both cheaper and better; hold() is the tool for LED1 and LED2.

duty() reports what you asked for, not what the pin is doing. led.duty() (modgpio.c:485) returns led_duty[index], the last percentage handed to brightness() or hold(). On an unrouted pin the LED is dark by the time you read it, and duty() still says 40. That is the intended contract — it is a record of the request — but it is not a measurement.

Step by step

Step 1 — Find out what the board thinks it has

Example (authored — no shipped call site)
import gpio
info = gpio.board_info()
print(info['name'], info['leds'], info['buttons'])
print(info['led_names'])
print(info['btn_names'])
What you should observe
PSoC Edge AI Dev Kit 5 1 (modgpio.c:61-65 and :625), then ['LED1', 'LED2', 'RGB_RED', 'RGB_BLUE', 'RGB_GREEN'], then ['SW2']. Write loops against gpio.num_leds() (:613) rather than a hard-coded 5 — the table is #ifdef-gated and a board with fewer LEDs is a legal build.

Step 2 — On, off, toggle

Example (authored — no shipped call site)
import gpio, time
led = gpio.led(0) # LED1
led.on(); time.sleep_ms(300)
led.off(); time.sleep_ms(300)
led.toggle()
print(led.name(), led.value())
What you should observe
The LED follows, and value() reads the pin back rather than a shadow (modgpio.c:322-325). On screen, the GPIO and RGB page updates with each call — that is gpio_ipc_send_led_state() at the end of every method. An index outside 0..num_leds()-1 raises ValueError naming the range (modgpio.c:591-594).

Step 3 — See the two brightness mechanisms in one session

This is the step that teaches the chapter. Run it on an RGB channel first, then on LED1.

Example (authored — no shipped call site)
import gpio, time
rgb = gpio.led(2) # RGB_RED — has a TCPWM route
rgb.brightness(20); time.sleep(2) # dim, and it STAYS dim
rgb.brightness(80); time.sleep(2) # brighter, and it STAYS
rgb.brightness(0)
led1 = gpio.led(0) # LED1 — no route
led1.brightness(20) # one 12 ms pulse, then dark
time.sleep(1)
led1.hold(20, 2000) # the same 20%, held for 2 s
led1.hold(80, 2000) # visibly brighter than the line above
What you should observe
On RGB_RED: two clearly different steady levels, each holding until the next call, with no flicker and no pause in the REPL. On LED1: the first brightness(20) is a blink you may not even catch, and the LED is dark afterwards — not dim, dark. Then the two hold() calls give you two distinguishable steady levels for two seconds each. If the two hold() levels look identical to you, the LED is likely near the top of its response curve; try 10 and 90.
What you should not conclude
That brightness() is broken on LED1. It did exactly what a 12 ms pulse looks like. The mechanism, not the call, is the difference.

Step 4 — duty() is a record, not a reading

Example (authored — no shipped call site)
import gpio
led1 = gpio.led(0)
led1.brightness(40)
print(led1.duty()) # 40 — even though the LED is now dark
What you should observe
40. The pin is low. Both facts are true, and the second is why hold() exists.

Step 5 — Read the button

Example (authored — no shipped call site)
import gpio, time
btn = gpio.button(0)
print(btn.name()) # 'SW2'
while True:
if btn.is_pressed():
print("pressed, raw =", btn.value())
time.sleep_ms(200)
time.sleep_ms(20)
What you should observe
SW2, then one line per press. is_pressed() is active-low — it compares against CYBSP_BTN_PRESSED (modgpio.c:520-526) — so value() reads 0 while the button is down. There is no debounce in this module; the 200 ms sleep above is doing that job. (The QWA309 buttons in J5 — The QWA309 base board: pots, buttons, RGB matrix, header are debounced, in software, with a 50 ms stable window — the two button APIs on this board do not behave the same way, and that is worth knowing before you port code between them.)

Traps

Warning
brightness() on LED1 or LED2 blocks the VM for ~12 ms and ends dark. It is not a level, it is a pulse. Use hold() for a level, or move to an RGB channel where the hardware can hold it.
hold() never uses the hardware PWM, even on a pin that has a route. On RGB_*, prefer brightness().
duty() is the last request, not the pin state.
gpio_ipc_msg is shared, non-static, with modoptiga.c. modgpio.c:104-107 says so in as many words: both modules only send from the MicroPython task, so they are never concurrent, and the shared-memory region is too small on some kits to afford one buffer per module. It works because of a single-task assumption. Send an LED state update from anywhere other than the MicroPython task and you can corrupt an OPTIGA touch pause in flight. Recorded as Appendix X #24 — Appendix X — Traps and anti-patterns.
Do not name the button SW1. CYBSP_USER_BTN1 = CYBSP_SW1 is a macro alias, not a silkscreen. The module reports "SW2" and the board agrees (modgpio.c:53-58).
Do not hard-code 5 LEDs. led_table[] is #ifdef-gated per LED; ask gpio.num_leds().
