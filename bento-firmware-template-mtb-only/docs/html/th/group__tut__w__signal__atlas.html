เป้าหมายของหัวข้อนี้

จำแนกให้ออก — ไม่ใช่ทำให้เกิด — รูปแบบอาการ (signature) ของความล้มเหลวทุกแบบที่บอร์ดแสดงได้ เมื่อได้ภาพถ่ายของ LED คำบรรยายหน้าจอ หรือผลบันทึกคอนโซลมา ต้องบอกชื่อสถานะนั้นและไฟล์ที่ทำให้เกิดได้ ที่ใดมีวิธีจำลองอาการอย่างไม่เป็นอันตราย ก็จะให้ไว้ ที่ใดไม่มี ก็จะไม่ประดิษฐ์ขึ้นเอง

ลำดับการทำงานจริงของเฟิร์มแวร์

บทนี้ไม่มีลำดับเดียว แต่เป็นตารางสำหรับเปิดหา สร้างจากสามแหล่งโดยอ้างอิงครบทุกแหล่งได้แก่ ข้อเท็จจริงตั้งต้นเรื่องการปิดเสียง printf บน CM33_NS, ตาราง LED ใน proj_cm55/main.c และรหัสขั้นตอนของจอแสดงผลในตัวควบคุมจอแสดงผลของ CM55 (TESAIoT_KIT_PSE84_AI-Micropython-BentoClaw/proj_cm55/modules/lvgl_display/controller/tesaiot_display.c — คอมไพล์รวมอยู่ใน libbento_cm55.a เทมเพลตส่งมอบ archive (ไฟล์ไลบรารีแบบสแตติก .a) ไม่ได้ส่งไฟล์ซอร์สมาด้วย)

กฎคือ เทียบข้อความให้ตรงตัวและดูรูปแบบการเรียก ห้ามเทียบเพียงคำนำหน้า #define printf(...) แบบฟังก์ชันปิดเสียง printf(...) รูปธรรมดาในไฟล์นั้น แต่ไม่ปิด (printf)(...) ที่ใส่วงเล็บไว้ — ไฟล์ที่ปิดเสียงเหล่านั้นใช้ (printf) โดยเจตนาตรงบรรทัดที่ต้องรอด

ทีละขั้น

ขั้นที่ 1 — จำแนกผลบันทึกคอนโซล

นำผลบันทึกคอนโซลจากบท A1 มาชุดหนึ่ง สำหรับทุกบรรทัดที่ขึ้นต้นด้วยคำนำหน้าในวงเล็บเหลี่ยม ให้ค้นหาบรรทัดนั้นในตารางที่ ข้อเท็จจริงตั้งต้น: อะไรพิมพ์ออกมาได้บ้าง หากไม่อยู่ในแถว LIVE แสดงว่าสิ่งที่เห็นไม่ใช่ผลลัพธ์ของเฟิร์มแวร์ชุดนี้

สิ่งที่ควรสังเกต
บน mtb-only ผลบันทึกที่ปกติคือบรรทัด [HB] t=lus tasks=u ทุก 10 s เท่านั้น ไม่มีอย่างอื่น บน mtb-mpy จะได้ [MPY] GC heap u KB @ p in s หนึ่งบรรทัดตามด้วยพรอมป์ REPL ส่วนบรรทัด [BOOT] … failed, storage: หรือ ERROR: ใด ๆคือความล้มเหลวจริง และจะถูกพิมพ์ออกมาเสมอ

ขั้นที่ 2 — จำแนกรูปแบบการกะพริบของ LED

นับจำนวนครั้งที่กะพริบและจับจังหวะเวลา แล้วเทียบกับ รหัส LED ของ CM55

สิ่งที่ควรสังเกต
LED2 ดับพร้อมกับตารางหน้า Home ปรากฏ คือความสำเร็จ ส่วน LED2 ที่กะพริบซ้ำ N ครั้งพร้อมจอดับ คือความล้มเหลวที่ขั้นใดขั้นหนึ่งของจอแสดงผลโดยที่ IPC ยังมีชีวิตอยู่ — คอนโซลของ CM33 ยังทำงานได้ และบน mtb-mpy ui._diag() ยังตอบได้ เพราะ IPC pipe ตั้งขึ้นก่อนจอแสดงผล (บท B2)

ขั้นที่ 3 — จำลองอาการเดียวที่ไม่เป็นอันตราย

รูปแบบอาการของความล้มเหลวที่มีวิธีทำซ้ำอย่างปลอดภัยมีเพียงแบบเดียว คือจอดับหลังการแฟลช ให้รัน make program แล้ว ห้ามตัดไฟจ่ายไฟใหม่

สิ่งที่ควรสังเกต
programmer รายงาน verified … bytes พาเนลยังดับอยู่ และบน mtb-only [HB] เริ่มเต้นอยู่ดี (คอร์กำลังทำงาน สิ่งที่ดับคือ backlight) เมื่อตัดไฟแล้วจ่ายไฟใหม่ หน้าจอจะปรากฏ ถึงตรงนี้ก็ได้เห็นสภาพที่ดูเหมือนการแฟลชล้มเหลวมาแล้วอย่างไม่มีอันตราย

ไม่มีการให้วิธีทำซ้ำสำหรับรหัส LED บอกความผิดพลาด marker ใน SRAM หรือลูปจากการต่อดีบักเกอร์ สิ่งเหล่านี้มีไว้จำแนก ไม่ใช่มีไว้ทำให้เกิด
